## 0. 데이터 스키마 메모 (재현에 필요)

- 각 jsonl 라인은 `{"type": ..., "timestamp": <ISO string>, ...}` 봉투(envelope). `type:"message"` 이고 `message.role:"assistant"`인 엔트리 중 `message.stopReason:"error"`가 에러 턴이다.
- 에러 턴은 `message.errorMessage`(원문 provider 에러 텍스트), `message.errorStatus`(있을 때 429 같은 HTTP 코드), `message.retryRecovery`(호스트 자체 auto-retry 기록: `{kind, status, attempt, recoveredAt, supersededBy}` — 있으면 같은 스트림 내에서 자동 복구됨, 없으면 이 턴 자체는 호스트 auto-retry로 복구되지 않음)를 가진다.
- **`auto_retry_start`/`auto_retry_end` 타입 엔트리는 코퍼스 전체(28,982개 message + 16,496개 custom 등 전 타입 포함)에서 0건** — deep-dive 조사에서 이미 확인된 "auto_retry는 세션 엔트리로 기록되지 않는 이벤트"라는 관측을 이번 전수 스캔으로 재확인. 따라서 P1 분석은 `stopReason:"error"` 턴 자체와 `retryRecovery` 필드에 전적으로 의존.

### 4-2. retry-after-ms 값 자체의 군집 — 계정 단위 공유 한도의 직접 증거

`retry-after-ms`를 파싱할 수 있었던 57건(35.4%)의 값을 정렬하면 명확히 3개 구간으로 나뉜다:

| 구간 | 범위 | 성격(추정) |
|---|---|---|
| 짧음 | 5~35초 | 초당/분당 요청 속도 제한(순간 버스트) |
| 중간 | 415초~8.2시간 | 5시간/일 단위 토큰 예산 계열 |
| 김 | 41.1~48.6시간 (15건) | 주간 단위 계정 사용량 한도로 추정 |

결정적 증거: **같은 세션 안에서, 그리고 서로 다른 두 프로젝트(lets-craft ↔ Smoody-platform) 사이에서, 거의 동일한 `retry-after-ms` 값이 반복 관측된다.** 예:
- 2026-07-14 17:22:47(lets-craft 메인)과 17:23:00(lets-craft 서브 `CriticTestR3`)이 **13초 차이로 거의 동일한 잔여시간(7034s→7018s, 차이 16초=경과시간과 정합)**을 보고 — 동일 리셋 시점을 서로 다른 호출자(메인+서브)가 동시에 맞고 있음.
- 2026-07-14 19:48:52(서브 `PlanCritic`)와 19:50:03(서브 `PlanCritic2`)이 71초 간격으로 54,668s→54,598s(차이 70초, 경과시간과 정합) — 서로 다른 서브에이전트 2개가 동일 리셋 시점.
- **2026-07-17 02:24(lets-craft 메인, retry-after 48.6h)과 03:00(Smoody-platform 메인, retry-after 48.0h)** — 서로 다른 프로젝트의 두 메인 세션이 30여 분 간격으로 거의 동일한(약 반나절 오차 내) 리셋 시점을 보고. 두 프로젝트는 같은 Anthropic 계정을 공유할 뿐 코드/세션상 아무 관계가 없다.
- lets-craft의 2026-07-17T02-09-33 세션 내에서는 `retry-after` 값이 48.6h → 47.1h → 45.6h → 44.1h → 42.6h → 41.1h로, 약 1.5시간 간격의 재시도마다 **일관되게 감소**(고정된 미래 리셋 시각을 반복 조회) — 단발성 오류가 아니라 하나의 고정 리셋 이벤트를 여러 차례 재확인한 기록.

이는 **계정(또는 API 키) 단위로 공유되는 사용량 한도**가 존재하고, 그 한도가 소진되면 **동시에 실행 중인 모든 호출자(메인 세션 + 모든 서브에이전트 + 심지어 다른 프로젝트의 별도 세션까지)가 동시에 429를 맞는다**는 것을 강하게 시사한다. 따라서 "병렬 스폰 수↑ → 429 위험↑" 가설은, 정확히는 "병렬 스폰 수↑ → 공유 한도 소진 속도↑ → 소진 시 동시 피해자 수↑"로 정교화해야 한다: 병렬 스폰 자체가 항상 429를 유발하는 것은 아니지만, 일단 계정 한도가 소진되면 그 순간 활성 중이던 모든 병렬 스폰이 일괄 피해를 입는다.

## 5. 판정: 우연(일회성) vs 구조적 반복

### 결론: **구조적 반복 패턴 (STRUCTURAL / RECURRING)**

근거:
1. 개별 턴이 아니라 **스톰 단위로도 23회**, 그리고 **관측된 8개 활동일 중 4일(50%)** 에서 재발 — 단일 사건이 아니다.
2. 최소 5회, 2개 프로젝트, 3개 날짜(07-14/16/17)에서 **동일한 실패 시그니처**(429/overloaded, retryRecovery 없음, 다음 엔트리까지 24분~6.6시간 침묵)가 독립 재발 — U1이 표적으로 삼는 "메인 세션 429 크래시 후 무한 정지"는 우연한 1회성이 아니라 반복되는 실패 모드다.
3. §4-2의 계정 단위 공유 한도 증거(교차 프로젝트 동시 429, 감소하는 retry-after 시계열)는 이 실패 모드가 **개별 세션의 운/설정이 아니라 계정 자원 구조**에서 비롯됨을 보여준다 — 즉 "이번엔 우연히 겹쳤다"가 아니라 유사한 강도의 병렬 작업을 계속하는 한 **재현 가능한 구조**다.
4. 429 + overloaded가 전체 에러 턴의 83.3%로 압도적 다수(vs 순수 네트워크 결함 0.6%) — provider 용량 계열이 예외가 아니라 지배적 카테고리.

단서(균형을 위한 반증 검토):
- 07-10~07-13(37세션)과 07-18(3세션) 도합 40개 세션에서는 에러가 전무했다 — "모든 세션에서 상시 발생"은 아니며, 특정 기간(계정 한도 소진~복구 사이)에 몰린다는 뜻이다. 이는 "구조적 반복"의 반박이 아니라 **메커니즘(공유 계정 한도)과 정합**한다 — 한도가 남아있으면 발생하지 않고, 소진되면 모든 동시 호출자가 함께 겪는다. lets-craft의 pre-craft/craft/post-craft 워크플로우는 본질적으로 다중 서브에이전트 병렬 스폰을 상시 사용하므로, 유사 강도의 작업이 반복되는 한 이 구조적 조건(공유 한도 소진)도 다시 발생할 것으로 예상된다.

### C1 무인 자동재개 플래그(CS-7) 활성화 권고: **활성화 권장**

위 판정에 따라 U1의 타이머 기반 무인 자동재개는 (계획 CS-7이 명시한 게이트 조건대로) **활성화 대상**이다. 다만 이번 분석에서 드러난 아래 사실을 U1 구현 시 **CS-8 보강**으로 반영할 것을 권고한다(계획 변경이 아니라 계획이 이미 예정한 CS-8의 파라미터를 실측으로 구체화):

- **retry-after 값의 동적 범위가 5초~48.6시간(약 3.5자릿수)** 로 극단적으로 넓다. CS-8은 이미 "재개 대상은 provider-wait 시그니처에 한정"이라고 규정했지만, 이 시그니처 안에서도 **retry-after가 비정상적으로 큰 경우(관측상 41시간 이상 구간이 15/57=26%로 드물지 않음)에는 "타이머 기반 대기 후 자동재개"가 아니라 즉시 notify-only로 강등**하는 상한 컷오프(예: 1~2시간)를 추가하는 것이 안전하다 — 그렇지 않으면 워치독이 세션을 최대 이틀간 "재개 대기 중"으로 붙잡아 둘 수 있다.
- 60.2%의 에러 턴이 `retryRecovery` 없이도 후속 엔트리로 이어졌다는 사실(§1)은, 실제로는 사람의 개입("계속해")이나 오케스트레이터 재시도가 그 공백을 메웠다는 뜻이다. U1이 이 수동 개입을 자동화로 대체하는 것이 정확히 이번 분석이 뒷받침하는 개선 방향이다.
